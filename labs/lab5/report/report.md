# Цель работы

Построение простейших моделей сети на базе коммутатора и маршрутизаторов FRR и VyOS в GNS3, анализ трафика посредством Wireshark

# Выполнение

Для начала запустим GNS-VM и GNS клиент, после чего создадим проект (рис. [-@fig:001]).

![Создание проекта](image/1.png){#fig:001 width=70%}

В проекте сделаем такую схему. Эта схема состоит из 2 терминалов, связанных между собой свитчём (рис. [-@fig:002]).

![Схема сети](image/2.png){#fig:002 width=70%}

Запустим первый терминал. В нём мы настроим айпи следующим образом, как показано на экране. Адрес - 192.168.1.11, шлюз - 192.168.1.1 (рис. [-@fig:003]).

![Настройка первого терминала](image/3.png){#fig:003 width=70%}

Ровно таким же способом настроим второй терминал, но ему дадим адрес 192.168.1.12. После этого попытаемся пингануться на первый терминал. Как видим, пакеты прошли (рис. [-@fig:004]).

![Настройка второго терминала и пинг](image/4.png){#fig:004 width=70%}

Теперь остановим все устройства (рис. [-@fig:005]).

![Остановка всех устройств сети](image/5.png){#fig:005 width=70%}

Перед повторным запуском сети мы начнём захват пакетов кабеля, идущего от первого терминала к свитчу (рис. [-@fig:006]).

![Запуск захвата пакетов](image/6.png){#fig:006 width=70%}

Выберем имя для файла дампа (рис. [-@fig:007]).

![Подтверждение начала захвата](image/7.png){#fig:007 width=70%}

После этого откроется Wireshark (рис. [-@fig:008]).

![Wireshark](image/8.png){#fig:008 width=70%}

Теперь мы запустим всю сеть (рис. [-@fig:009]).

![Запуск всех устройств сети](image/9.png){#fig:009 width=70%}

Теперь посмотрим на вывод Wireshark. Как мы видим, после запуска сети каждый терминал отправил несколько Gratuitous ARP пакетов. Это пакеты, которые устройство отправляет самому себе, оповещая всех участников сети о своём существовании (рис. [-@fig:010]).

![Gratuitous ARP](image/10.png){#fig:010 width=70%}

Откроем второй терминал и попробуем отправить первому терминалу один echo запрос через ping с помощью протокола icmp (рис. [-@fig:011]).

![Ping через ICMP](image/11.png){#fig:011 width=70%}

В Wireshark обнаружим пару пакетов запрос-ответ по протоколу icmp (рис. [-@fig:012]).

![Новые пакеты в Wireshark](image/12.png){#fig:012 width=70%}

Разберём подробнее один из пакетов. В ICMP фрагменте мы видим тип 8 (echo (ping) request). Поле Data содержит простой набор байтов, шаблонный (рис. [-@fig:013]).

![Анализ ICMP пакета](image/13.png){#fig:013 width=70%}

Рассмотрим обратный пакет. Он будет сильно похож на предыдущий, но уже будет идти не от 2 терминала к первому, а наоборот. И тип уже будет 0 (echo (ping) reply) (рис. [-@fig:014]).

![Анализ второго ICMP пакета](image/14.png){#fig:014 width=70%}

Теперь осуществим ping по протоколу udp (рис. [-@fig:015]).

![ping по протоколу udp](image/15.png){#fig:015 width=70%}

В Wireshark появится пара пакетов по протоколу UDP, опять же, формата запрос-ответ (рис. [-@fig:016]).

![UDP пакеты](image/16.png){#fig:016 width=70%}

Рассмотрим их по подробнее. У UDP в графе Data уже немного другой набор байтов. Кроме того, теперь есть информация о портах (рис. [-@fig:017]).

![UDP пакет](image/17.png){#fig:017 width=70%}

Второй пакет идентичен, но отправитель и получатель поменялись местами (рис. [-@fig:018]).

![Второй UDP пакет](image/18.png){#fig:018 width=70%}

Попробуем осуществить ping по TCP. Видим немного необычный вывод. Сначала устанавливается воединение (хендшейк), после чего отправляется пакет, и соединение закрывается (рис. [-@fig:019]).

![ping по TCP](image/19.png){#fig:019 width=70%}

В Wireshark это выглядит следующим образом. Первые 3 пакета по tcp это процесс установки соединения, потом идёт наш эхо пакет в сторону первого терминала, после чего первый терминал отправляет ответом не echo ответ, а обычный пакет TCP с флагом ack, что означает, что ответ был получен. После этого последние 3 пакета нужны для закрытия соединения (рис. [-@fig:020]).

![TCP пакет](image/20.png){#fig:020 width=70%}

Рассмотрим echo пакет TCP. Как видим, тут содержится информация о портах, флагах tcp, а также поле Data. Оно содержит совсем другой набор байт, нежели ICMP и UDP (рис. [-@fig:021]).

![TCP Echo пакет](image/21.png){#fig:021 width=70%}

![Настройка терминала](image/30.png){#fig:030 width=70%}

![Айпи eth0](image/32.png){#fig:032 width=70%}

![Ping к роутеру](image/33.png){#fig:033 width=70%}

Как видим, было 5 пар echo пакетов формата запрос-ответ от клиента к роутеру и от роутера к клиенту (рис. [-@fig:034]).
